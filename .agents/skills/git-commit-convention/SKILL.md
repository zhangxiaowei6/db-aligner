# Git 提交规范

## 适用任务

用于准备新的 Git 提交、拆分提交、检查提交消息或根据已有差异拟定提交主题。提交前阅读[仓库约定](../../../AGENTS.md)和[贡献说明](../../../CONTRIBUTING.md)，按实际修改范围使用 `verification` 完成检查。

## 消息格式

使用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/) 的消息结构：

```text
<type>[(scope)][!]: <中文描述>

[可选：中文正文]

[可选：中文脚注]
```

- `type` 使用英文小写。规范定义 `feat` 和 `fix`，本技能同时约定使用常见类型 `docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore` 和 `revert`。
- `scope` 用于指出受影响的模块、层或目录，可使用稳定的项目标识，例如 `desktop`、`engine`、`protocol`；没有明确范围时省略。
- 主题必须使用中文描述实际结果，简洁、具体、使用动词开头，不以句号结尾；不要只写“修改代码”“优化”等无法判断内容的文字。
- 破坏性变更使用 `type(scope)!: 描述`，无范围时使用 `type!: 描述`；规范允许通过 `!` 或 `BREAKING CHANGE` 脚注标记，本技能约定同时提供 `BREAKING CHANGE: 中文说明` 以记录迁移影响或兼容处理。
- 正文和脚注使用中文；代码标识、命令、接口名、路径和协议字段保留原文，用反引号包裹。
- 每个提交保持单一目的。无关的格式化、重命名或生成文件不要混入同一提交。

## 类型选择

| 类型       | 使用场景                           |
| ---------- | ---------------------------------- |
| `feat`     | 增加面向用户或调用方的新能力       |
| `fix`      | 修复错误、回归或不符合预期的行为   |
| `docs`     | 只修改文档、注释或技能说明         |
| `style`    | 不改变运行行为的代码格式调整       |
| `refactor` | 不改变外部行为的代码结构调整       |
| `perf`     | 改善性能且不改变预期功能           |
| `test`     | 新增、修改或整理测试               |
| `build`    | 构建工具、依赖或产物配置变更       |
| `ci`       | 持续集成或自动化检查配置变更       |
| `chore`    | 其他不属于上述类型的维护工作       |
| `revert`   | 回退已有提交；主题说明被回退的提交 |

当一个差异同时涉及多个类型时，按主要用户可见结果选择类型；必要时拆成多个逻辑独立的提交。纯文档和技能改动优先使用 `docs`。

## 提交前流程

1. 查看 `git status`、工作区及暂存区的完整 diff，确定本次拟提交的范围，区分用户已有或其他任务的修改。
2. 检查是否包含凭据、私钥、真实会话、本地资料、SQL 档案、SQLite、依赖目录、构建产物或其他仓库明确禁止提交的文件。
3. 按逻辑目的选择 `type` 和 `scope`，拟定中文主题；需要时补充中文正文和 `BREAKING CHANGE` 脚注。
4. 先检查暂存区的 `git diff --cached`，确认路径、删除内容和生成文件均符合预期，再执行提交。
5. 用户未明确要求创建提交时，只准备并展示推荐消息，不运行 `git commit`；用户明确要求后仍应在提交前报告将要提交的范围。

## 示例

```text
feat(desktop): 支持按目标库预览选定同步 SQL
fix(engine): 阻止未知执行状态被标记为成功
docs(skills): 增加中文 Conventional Commits 提交规范
refactor(protocol): 统一比较任务响应的错误字段
test(engine): 补充中断执行后的恢复证据校验
feat(protocol)!: 移除旧版比较请求接口

BREAKING CHANGE: 调用方必须改用 `sync.compare.start` 请求
```

不要使用以下缺少事实信息的主题：`update code`、`修复问题`、`misc`、`提交代码`。
